# DSK Bank — ранкер продуктовых карточек

[![Open in Colab](https://colab.research.google.com/assets/colab-badge.svg)](https://colab.research.google.com/github/beckortikov/dsk-product-ranker/blob/main/demo.ipynb) [![Live dashboard](https://img.shields.io/badge/live%20dashboard-Hugging%20Face%20Space-blue)](https://huggingface.co/spaces/beckortikov/dsk-product-ranker)

*English version: [README.md](README.md)*

Лёгкий двуязычный (BG + EN) ранкер для Smart Search на dskbank.bg. Фронт
шлёт сырой запрос пользователя каждые 10 набранных символов; сервис отдаёт
ранжированный список карточек продуктов быстрее, чем за миллисекунду.

## Кратко: требования ТЗ → как закрыты

| требование | реализация |
|---|---|
| Ранжированный список `{document_id, product_name, product_summary, relevance}` | `POST /rank-product-cards`, контракт ниже |
| `product_summary` — короткий продающий месседж (в данных его нет) | извлекается офлайн из **hero-слогана** страницы (`##` сразу под заголовком — это собственный маркетинговый one-liner банка), 81/85 карточек; fallback — первое предложение блока «Какво представлява?»; опционально `--llm` — переписать через Claude |
| **Lightweight** (эмбеддинги — только как точка отсчёта) | чистый Python: BM25F + coverage-скоринг; **p50 0.1 мс, p95 0.3 мс** на запрос при 85 карточках; эмбеддинги используются только в `eval.py` как baseline |
| **Scalable** — легко добавлять/удалять карточки | каталог = один `products.json`; `PUT/DELETE /catalog/cards/{id}` или правка файла → индекс перестраивается in-process на следующем запросе, без переобучения и деплоя |
| **Болгарский и английский** | один индекс по обоим языкам каждой страницы; стемминг по алфавиту токена; транслитерация на лету (`kreditna karta`, `дск мобайл`) |
| Near-дубли (individual / business / corporate) | схлопнуты в одну карточку при сборке (201 страница → 85 карточек); все `document_id` сохранены, возвращается первый |
| Флагманы тонут в общих токенах (*DSK Mobile* vs «mobile») | на карточке: `priority_boost`, кураторские `aliases`, `exact_match_pins`, бонус за фразу/начало имени; **флагманские запросы: Hit@1 = 100 %** |
| Недописанный запрос (каждые 10 символов) | префиксное расширение последнего токена; терпимость к опечаткам (Damerau-Levenshtein ≤ 1–2) |

**Оценка** (73 двуязычных запроса + 10 негативных «не про продукты», `python eval.py`):

| система | Hit@1 | Hit@3 | MRR | abstain на негативах | p50 мс | p95 мс |
|---|---|---|---|---|---|---|
| только BM25F | 82.2 % | 87.7 % | 0.857 | 80 % | 0.08 | 0.12 |
| + префикс / опечатки / транслит | 90.4 % | 97.3 % | 0.937 | 80 % | 0.10 | 0.35 |
| **Наш** (+ алиасы, пины, бусты) | **98.6 %** | **100 %** | **0.993** | 80 % | 0.10 | 0.31 |
| Мультиязычные эмбеддинги, cosine (только референс) | 56.2 % | 74.0 % | 0.648 | 100 % | 29.6 | 56.3 |

Hit@1 по типам запросов у нашего ранкера: флагманы 100 %, generic-токены 100 %, обычные продукты 100 %, префиксы 100 %, кросс-язык 100 %, транслит 100 %, опечатки 80 %, вопросы естественным языком 100 %.

Embedding-референс (`paraphrase-multilingual-MiniLM-L12-v2`, ONNX, `python eval.py --embeddings`) — это то место, где ТЗ разрешает семантические модели: как точка сравнения. На этом каталоге он проигрывает лексическому ранкеру по всем типам, кроме одиночных generic-слов, и **не решает проблему флагманов** (29 % Hit@1 — DSK Mobile / Smart / Online / Business эмбеддятся почти одинаково), при этом стоит ~100× по латенси и 120 МБ модели в рантайме. Это и есть аргумент держать семантику *офлайн* (алиасы, summary), а рантайм — лексическим. Полная таблица: `eval_results_full.md`.

### Проверка на переобучение (held-out)

Набор из 73 запросов выше — **dev-set**: его писал тот же человек, что и тюнил
ранкер по его промахам, а пины/алиасы флагманов буквально содержат часть его
запросов (14/73 попадают в `exact_match_pin`). Поэтому `python eval.py --holdout`
генерирует второй набор **механически из каталога** (seed 0, без ручного
отбора, по нему ничего не тюнилось): полные BG/EN имена, префиксы 55 %,
опечатки-перестановки соседних букв, транслитерированные имена, случайные пары
слов из имени и hero-слоганы как запросы. 770 запросов.

| система | Hit@1 | Hit@3 | MRR | префикс | опечатка | транслит | пара слов | слоган |
|---|---|---|---|---|---|---|---|---|
| только BM25F | 76.5 % | 86.8 % | 0.816 | 74–80 % | 71–73 % | 16 % | 80 % | 88–90 % |
| + префикс / опечатки / транслит | 91.7 % | 98.4 % | 0.950 | 78–86 % | 99 % | 95 % | 80 % | 88–90 % |
| **Наш** | **91.9 %** | **98.4 %** | **0.952** | 78–86 % | 99 % | 98 % | 80 % | 88–90 % |
| Эмбеддинги (референс) | 54.4 % | 74.8 % | 0.665 | 22–43 % | 51–57 % | 44 % | 37 % | 64–71 % |

Что это значит, честно:

* Цифра на кураторском наборе (98.6 %) оптимистична примерно на 7 пунктов;
  **91.9 % Hit@1 / 98.4 % Hit@3** — честная оценка на формах запросов, которые
  никто не подбирал руками. Разрыв сосредоточен в *префиксах* и *парах слов* —
  они объективно неоднозначны (55 % от «Застраховка „Кредитна защита“ за…»
  подходит трём продуктам); Hit@3 = 98.4 % показывает, что gold почти всегда рядом.
* Ручной конфиг флагманов (пины + алиасы) даёт **+8 пунктов на кураторском
  наборе и +0.2 на held-out**: он закрывает конкретное бизнес-требование
  (DSK Mobile должен побеждать «mobile»), а не надувает общее качество. Общий
  прирост дают универсальные механизмы (префикс / опечатки / транслит): 76.5 → 91.7.
* Embedding-референс далеко позади на обоих наборах, так что вывод
  «лексика vs семантика» — не артефакт dev-set'а.
* Обучаемых параметров нет; то, что тюнилось руками (веса полей, размеры бонусов,
  пороги), тюнилось на dev-set. Перед продом тестовым набором становится реальный
  лог запросов банка — лог дашборда/API сделан именно под это.

## Как это работает

```
 офлайн (build_catalog.py)                        рантайм (ranker.py, каждые 10 символов)
 ─────────────────────────────                    ─────────────────────────────────────────
 df_data.csv + df_mapping.csv                     POST /rank-product-cards {query, top_k}
   │ пары BG ↔ EN                                    │
   │ схлопывание вариантов по типу клиента           ▼
   │ чистка <img>/хлебных крошек/markdown         токенизация (BG/EN по алфавиту, стемминг, стоп-слова)
   │ hero-слоган → product_summary                   │  по токену: exact ▸ prefix (последний) ▸ translit ▸ fuzzy
   │ URL-крошки → category                           ▼
   │ кураторские alias'ы + TF-IDF keywords        скоринг каждой карточки
   │ бусты и пины флагманов                          relevance = idf-взвешенное покрытие полей ∈ [0,1]
   ▼                                                            × специфичность + бонус фразы/начала + буст
 products.json  ───────────────────────────►        tie-break = BM25F
 (hot-reload по mtime)                                пины → 1.0
                                                     ▼
                                                  отсечь < min_relevance, top_k
```

### Скоринг — зачем два скора

BM25 хорошо *ранжирует*, но его абсолютное значение ничего не говорит фронту,
которому надо решить «показывать карточку или нет» на полунабранный запрос.
Поэтому у каждой карточки:

* **`relevance`** — idf-взвешенное **покрытие полей**: для каждого терма запроса
  берём вес лучшего поля, где он найден (`name` 1.0 · `aliases` 0.6 ·
  `category` 0.5 · `summary` 0.4 · `keywords` 0.3 · `body` 0.2), с дисконтом
  за качество матча (exact 1.0 · prefix 0.85 · translit 0.75 · fuzzy 0.6),
  усредняем по idf-массе запроса. Токены, не нашедшиеся нигде, считаются с
  половинным весом (поэтому `credit crad` < `credit card`). Дальше: фактор
  специфичности (какую долю *имени* карточки покрыл запрос), +0.15 если запрос —
  подстрока имени, ещё +0.10 если имя с него *начинается*, `+0.2·(priority_boost−1)`,
  `exact_match_pins` → 1.0.
  Итог: 1.0 = «карточка так и называется», ~0.2 = «слова где-то встречаются на
  странице». Сопоставимо между запросами → работает один порог.
* **BM25F** (насыщение tf, idf, нормализация длины, веса полей) разводит ничьи
  между карточками с одинаковым покрытием — например пять кредитных карт.

### Понимание запроса (всё в рантайме, без ML)

| пользователь печатает | что происходит |
|---|---|
| `dsk mob` | последний токен расширяется по префиксу по «ядру» словаря (name/aliases/category/summary; body — только если больше ничего) |
| `кредитна крата`, `mtokn` | Damerau-Levenshtein ≤ 1 (≤ 2 от 7 символов) по ядру словаря, первая буква должна совпадать |
| `kreditna karta`, `дск мобайл`, `депозит` | транслитерация латиница↔кириллица, потом снова exact/prefix/fuzzy |
| `DSK Mobile`, `мобилно банкиране` | `exact_match_pins` на флагмане → relevance 1.0, гарантированное #1 |

### Бизнес-нюансы

* **Near-дубли.** Страницы для individual / business / corporate — один продукт.
  `build_catalog.py` группирует по стеммированному каноническому имени без
  суффиксов типа клиента и дополнительно склеивает пары с одинаковым EN-именем,
  *если* BG-имена вложены («Бинарна опция» ⊂ «Бинарна валутна опция») — но не
  два разных «Loan Protection Insurance». 201 страница → 85 карточек; карточка
  хранит все `document_id`, наружу отдаёт первый.
* **Флагманы.** DSK Mobile / Smart / Online / Business / Direct / mToken несут
  `priority_boost`, кураторские двуязычные `aliases` («мобилно банкиране»,
  «mobile banking», «мобайл») и `exact_match_pins`. Всё это лежит в
  `products.json`, то есть это контент, а не код — команда банка крутит без
  деплоя. Абляция показывает цену: Hit@1 по флагманам 79 % → 100 %.
* **Кросс-языковой recall.** Оба языка страницы в одной карточке, поэтому EN-запрос
  находит BG-only страницу (DSK Mobile и DSK Online существуют только на BG)
  через алиасы, категорию и текст; BG-запрос находит EN-имена через транслит + fuzzy
  («депозит» → «deposit»).

## Прод (system design)

* **Зависимости рантайма:** `snowballstemmer`, `rapidfuzz`, FastAPI. Без torch,
  без файлов моделей, образ ~50 МБ. Индекс на 85 карточек строится ~100 мс, память < 20 МБ.
* **Латенси:** p50 0.1 мс / p95 0.3 мс in-process; end-to-end на localhost — единицы мс.
  Одинаковые `(query, top_k, min_relevance, catalog_mtime)` отдаются из LRU на 4096
  записей — поллинг каждые 10 символов от многих пользователей бьёт в одни и те же префиксы.
* **Жизненный цикл каталога.** `products.json` — деплоируемый артефакт.
  Добавить/удалить = `PUT/DELETE /catalog/cards/{id}` (атомарная запись) или правка файла;
  каждый запрос сверяет mtime и перестраивает индекс под локом (чтение без лока;
  в ключе кэша есть mtime, устаревшее не отдаётся никогда). Для флота реплик:
  раздавать файл через object storage / config map, каждая реплика перечитывает; либо
  пушить через endpoint за админской авторизацией.
* **Ночная пересборка.** `build_catalog.py` прогоняется по свежему скрейпу и выдаёт
  новый `products.json`; diff по `card_id` — это release note. Кураторские поля
  (`aliases`, `priority_boost`, `exact_match_pins`, LLM-summary) мержатся из
  предыдущего каталога, а не генерируются заново.
* **Наблюдаемость.** Каждый запрос логируется JSON'ом `{q, k, ms, top}` плюс заголовок
  `X-Latency-Ms`; этот лог — сигнал для следующего раунда тюнинга (какие запросы
  abstain'ят, где низкая relevance, какой флагман кому проиграл). Лить в
  ClickHouse/BigQuery; алерты на p95 и на долю abstain.
* **Порог.** Фронту стоит скрывать карточки ниже `min_relevance` (дефолт 0.1;
  0.2–0.25 отрежет матчи только по body). Слабо связанные запросы намеренно получают
  0.2–0.4, чтобы UI мог показать их приглушённо или не показывать.
* **Рост каталога.** Линейный проход по карточкам на запрос — нормально до ~5 000
  карточек (≈ 20 мс). Дальше — инвертированный индекс по ядру словаря (все структуры
  уже term-keyed) или шардирование по сегменту клиентов.
* **Цикл качества.** На каждый репортнутый промах — кейс в `eval.py`; чинить
  сначала данными каталога (alias / pin), потом кодом. `pytest` охраняет контракт и
  поведение флагманов.
* **Лучшие summary.** `python build_catalog.py --llm` переписывает слоганы через Claude
  (`claude-opus-5`) офлайн; рантайм не меняется.

## Осознанные компромиссы

* Болгарский стемминг — консервативный rule-based суффикс-стриппер (у Snowball нет
  BG-алгоритма). Специально недостеммивает; для ~100 карточек хватает.
* Relevance — *не* вероятность, а калиброванный coverage-скор. Достаточно для
  «показать / приглушить / скрыть»; если UI нужны вероятности — позже подогнать
  изотоническую регрессию по кликам.
* Eval-набор собран руками (логов ещё нет); для generic-запросов gold принимает любую
  карточку, которую принял бы разумный пользователь (любая кредитная карта на «credit card»).
* Терпимость к опечаткам намеренно узкая (≥ 5 символов, совпадение первой буквы), чтобы
  запросы «не про продукты» не цеплялись за мусор; оставшиеся промахи на опечатках —
  спорные ничьи, а не потеря recall.
